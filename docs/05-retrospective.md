# 05 实现复盘与下一步

本页记录本版本实际实现中的问题与取舍，不代表候选人个人经历。

## 最难的问题

可靠回答需要同时处理“有没有原文”和“原文能否支持结论”。单纯检索命中不能当作已核验，版本更晚也不能自动当作优先依据。因此拆分 search 与 read，并在运行时要求引用来自本轮成功读取的原文。

另一难点是澄清状态：冲突追问需要呈现双方证据，但问题背景缺失时根本没有可引用的原文。最初的统一引用要求过强，测试后区分了这些情形。

## 学习与改进

能生成合适的输出格式，不意味着模型具备正确的工具决策能力。离线 Mock 很适合验证循环、状态和边界，却不能证明模型会主动补检索或正确识别冲突。相同 API 协议能工作，也不代表外部供应商已验证。

把模型和工具注入运行时后，可以独立验证“错误引用被拒绝”和“工具失败不登记证据”。资料修改测试比固定答案快照更能揭示答案是否真正依赖输入。不过当前环境的修改测试用的是 Mock，仍需在真实模型上重复；11 场景真实验收脚本已包含这两组修改资料用例。

## 下一步优先级

1. 接入真实模型，运行全部场景，保留至少两种真实决策路径和失败案例。
2. 人工核验答案与证据的语义支持，评估冲突遗漏和改写检索召回；对发现的问题修改提示与检索后复测。
3. 增加适用范围明确的多版本资料，检验模型能否按证据消解冲突，而不只是一律追问。
4. 若规模增大，再考虑 BM25/向量检索、分段与访问权限；有需求再增加 UI。

## 用时与未完成项

本环境的实测制作耗时和验证时间写在 examples/build-report.json。它是 AI 辅助制作耗时，不是候选人个人投入，也不包含未来真实模型验证、个人修改和 GitHub 提交。

尚未完成：真实模型运行及语义验收、候选人贡献记录、GitHub 远程 URL 和推送后的最终提交确认。不能把本版本描述为已经完全符合考核要求的最终提交。

## 本轮进一步改进

将“给出运行入口”补成“能实际产生验收材料”的完整流程：独立保存每次真实运行、核对输入/原文/源码摘要、检查具体事实和行为、自动报告失败，再连接到 GitHub 提交。这样既减少手工整理错误，也不会把未运行的模型测试写成成功。

增加了源码摘要失配检查，防止修改实现后仍沿用旧模型结果。个人填写与文档不应改变决策源码摘要，因此排除了个人记录文件，避免用户完成贡献披露后被无端要求再次付费验证。
