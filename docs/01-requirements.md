# 01 需求与成功标准

## 用户与问题

用户为合成企业员工。他们会用不同表达询问制度，或在上一轮基础上追问。资料可能存在版本冲突、缺少适用范围，也可能不包含所问事项。目标是返回能追溯原文的可靠答复，不以“总能回答”作为成功标准。

## 范围

输入为问题、可选历史，以及本地合成制度。每份制度包含 ID、标题、版本日期、适用范围和正文。提供文档检索和原文读取两个工具。输出答案、引用 ID、逐字原文、资料缺口、任务状态与执行记录。

范围包括正常回答、冲突追问、资料外问题、改写问题、上下文追问和工具失败。额外实现步数限制、读取证据校验、模型错误返回和离线入口。不包括 UI、线上部署、多 Agent、权限系统或生产级文档索引。

## 成功标准

| 验收点 | 可观察标准 |
|---|---|
| 明确答案 | 在 data/normal.json 的 D01 中读取到 30 天，回答并附真实原文 |
| 文档冲突 | D01 为 30 天、D02 为 15 天，引用双方并请求确认，不能自行采用较新版本 |
| 资料外问题 | 停车位分配无证据，说明缺口，不根据常识给结论 |
| 改写的相似问题 | “垫付之后最迟何时能报账”通过补充检索定位报销制度 |
| 上下文追问 | 对“期限是多久”结合报销历史检索并重新读取原文 |
| 工具失败 | 临时失败可尝试恢复；持续失败明确结束，失败读取不能生成可用证据 |
| 问题背景不足 | 只问“期限是多久”且没有历史时，先询问业务事项 |
| 执行上限 | 达到 max_steps 输出 incomplete，已取得的观察保留在 Trace |
| 引用核验 | 未读取文档、伪造原文不能通过完成动作验证 |
| 数据变更 | 修改原文后答案与引用同步变化；消除冲突后可以改变终止状态 |

这些标准必须在真实模型路径中再次验证；离线通过不意味着模型已经达标。

## 状态约定

`answered` 表示有原文支撑的回答；`needs_clarification` 表示等待用户补充；`insufficient_evidence` 表示现有资料不足；`tool_error`、`model_error`、`incomplete` 均表示任务未完成。用户追问通过 `--history` 提供，不在 CLI 进程内阻塞等待输入。
